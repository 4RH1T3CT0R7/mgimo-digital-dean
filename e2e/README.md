# T20. Сценарий жюри и проверки доступа

Требуются Node.js 22+, npm и Chromium. Из корня проекта:

```sh
npm --prefix e2e ci
cd e2e
npx playwright install chromium
npm run typecheck
```

Укажите `BASE_URL` HTTPS-стенда и передайте через окружение пароли к тестовым аккаунтам.

| Переменная | Аккаунт |
|---|---|
| `E2E_PASSWORD_STUDENT_MO` | `student.mo` |
| `E2E_PASSWORD_STUDENT_MEO` | `student.meo` |
| `E2E_PASSWORD_DEKANAT_MO` | `dekanat.mo` |
| `E2E_PASSWORD_DEKANAT_MEO` | `dekanat.meo` |
| `E2E_PASSWORD_ADMIN` | `admin` |

`npm run e2e` запускает оба проекта, `npm run e2e:mobile` — мобильный. HTML-отчёт в `playwright-report/`. Сценарии создают тестовые заявки. В S5 проверяется только лимит для заведомо несуществующего логина, уникального для запуска. Между прогонами заявления и попытки входа могут остаться в БД стенда. При многократных запусках подряд учитывайте общий лимит неудачных входов с одного IP из auth.

Расписание открывается через вкладку «Расписание», как у жюри, — на текущей неделе. В seed переносы есть на каждой неделе с 16 ноября по 6 декабря. Если данные стенда отличаются, задайте `E2E_SCHEDULE_DATE` в формате `YYYY-MM-DD`: после вкладки тест откроет неделю с этой датой. Для собственного локального HTTPS с тестовым сертификатом предусмотрен `E2E_LOCAL_HTTPS=1`, применимый только к loopback. `E2E_CHROMIUM_PATH` позволяет указать путь к локальному Chromium.

## Моки

Установите зависимости в `frontend/`, передайте пароли тестовых аккаунтов из документации моков и запустите из `e2e/`:

```sh
E2E_MOCK=1 npm run e2e
```

Потребуются тестовые пароли студента ФМО и сотрудника ФМО. Playwright запустит `dev:mock` на порту 4183. Если фронтенд находится в отдельной рабочей копии, укажите её каталог `frontend/` через `E2E_FRONTEND_DIR`. Для проверки страниц уведомлений, объявлений и дедлайнов в этом фронтенде нужны T11 и T13. Моки заявок сохраняют ответ и статус, поэтому эти шаги выполняются и на моках. Доставка уведомления о новом ответе и тест S1–S7 выполняются через реальный API, где работают JetStream и шлюз.

## CI

Workflow — `.github/workflows/e2e.yml`. Он запускается только вручную: Actions → e2e → Run workflow, на обычных PR не срабатывает. Собирает стек через Compose со случайными паролями БД, загружает seed, прогоняет оба проекта и сохраняет HTML-отчёт как артефакт `playwright-report`. Сценарий требует интегрированных T06, T11 и T13.

Перед первым запуском заведите в репозитории (Settings → Secrets and variables → Actions → New repository secret) пять секретов. Значения — пароли тестовых аккаунтов, соответствующие хешам в seed:

| Секрет | Аккаунт |
|---|---|
| `E2E_PASSWORD_STUDENT_MO` | `student.mo` |
| `E2E_PASSWORD_STUDENT_MEO` | `student.meo` |
| `E2E_PASSWORD_DEKANAT_MO` | `dekanat.mo` |
| `E2E_PASSWORD_DEKANAT_MEO` | `dekanat.meo` |
| `E2E_PASSWORD_ADMIN` | `admin` |

Без любого из них workflow останавливается с ошибкой «Не настроен …» до запуска тестов.

Уведомление «Ответ по заявке №…» ищется с фильтром «Заявки» и листанием «Показать ещё»: важные непрочитанные уведомления прошлых прогонов стоят в ленте выше. На `/notifications` проверка ширины ждёт загруженную ленту, а не кнопку «Ознакомлен(а)»: после подтверждения её нет. S7 сверяет и ключи JSON, и подстроки в тексте ответа.

## Отступления от таблиц T20

- Сотрудник ищет заявку по номеру, а не по тексту: поиск по контракту принимает номер или ФИО. Уникальный текст сверяется в карточке заявки.
- S5 использует логин `e2e.nobody.<uuid>`, а не `e2e.nobody`: лимит считается по логину, и повторный прогон не должен упираться в счётчик прошлого.
- S7 проверяет и ключи JSON, и подстроки `password`, `password_hash`, `token_hash` в `JSON.stringify(body)`.
