## П5. Контракты для параллельной работы трёх агентов

- **Дата:** 2026-11-08
- **Этап:** 5
- **Инструмент:** Claude Code
- **Задача ИИ:** описать API, события и модель данных так подробно, чтобы агенты трёх людей могли писать сервисы и фронтенд параллельно и их части состыковались.
- **Что получилось:** 7 OpenAPI-файлов (публичный API каждого сервиса + внутренние), каталог событий с шаблонами текстов уведомлений, таблицы всех БД, 9 бизнес-правил с указанием, что покрыть табличными тестами, тестовые данные с общими ID для всех сервисов.
- **Что ИИ нашёл сам:**
  - без отдельного порта внутренний API был бы доступен снаружи через шлюз (D31);
  - сотрудник мог бы создать объявление для группы чужого факультета, потому что `notifications` не знает факультет группы — добавлен внутренний эндпоинт `getGroup`.
- **Самопроверка:** линтер OpenAPI скачать не дали (ограничение среды), поэтому ИИ проверил ссылки `$ref` и уникальность `operationId` своим скриптом. Первый вариант скрипта упал на зарезервированном слове awk — исправлено.
- **Результат:** `docs/contracts/`, решения D31–D38.

## П6. План и ТЗ для агентов трёх участников

- **Дата:** 2026-11-08
- **Этап:** 7
- **Инструмент:** Claude Code
- **Задача ИИ:** разбить работу на задачи с приоритетами и для каждой написать ТЗ по шаблону, которое можно целиком вставить в Codex.
- **Как менялось по ходу:** капитан сначала попросил оставить себе всё критичное («Codex хуже Claude Code»). Затем уточнил, что одному не успеть, и разрешил отдать участникам сервисы при условии очень жёстких ТЗ. ИИ перераспределил работу так, что участники получили сервисы, которые лучше всего проверяются тестами (`academic`, `notifications`), а вход, заявки и инфраструктура остались у капитана.
- **Как сделали ТЗ «защищёнными от косяков агента»:**
  - таблицы тест-кейсов с конкретными входами и ожидаемыми значениями — это приёмка;
  - явный список каталогов, которые можно трогать;
  - условие «если контракт кажется неверным — остановись»;
  - разбиение на PR, чтобы задержка участника не блокировала капитана;
  - общий плейбук `docs/tasks/README.md` с готовым промптом и таблицей типичных ошибок агентов.
- **Самопроверка:** ИИ сверил ссылки плана с файлами задач и нашёл две устаревшие ссылки на номера задач после перенумерации — исправлено. В одном ТЗ он нашёл свои рассуждения, оставленные в таблице тест-кейсов вместо однозначного ожидания, — переписано.
- **Результат:** `docs/plan.md`, `docs/tasks/T01–T26`, `docs/tasks/README.md`, решения D43–D48.

  5. Скриншоты «после» в трёх размерах и двух темах — `design-after/`.
  6. Отдельный агент без контекста обсуждения получил файлы, скриншоты и чек-лист «нейрослопа» (шаблонные фразы, декоративные приёмы) и вернул таблицу находок; исправления — в том же PR.
- **Почему так:** ревьюер с чистым контекстом не «защищает» свои же решения; чек-лист превращает вкусовое «слоп или нет» в проверяемые пункты.

## П9. T04 PR1: внутренний API academic по контрактам

- **Дата:** 2026-11-09
- **Участник и инструмент:** Всеволод Омельченко, Codex.
- **Ключевой запрос:** «Начинай работу». Перед этим участник передал ссылку на репозиторий и попросил разобрать свою часть; первым этапом выбран T04 PR1.
- **Контекст агенту:** `AGENTS.md`, `docs/tasks/README.md`, `docs/tasks/T04-academic.md`, эталон `services/auth`, контракты и общие ID из `docs/contracts/`. Объём — только PR1, без публичных экранов и API из PR2.
- **Что получилось:** миграция всех 13 таблиц academic и откат; четыре внутренних обработчика strict-server на 8081; SQL-запросы и сгенерированные sqlc-обёртки; запуск с миграциями и readiness; seed с двумя тестовыми профилями, 18 одногруппниками без аккаунтов, справочниками и 12 вымышленными преподавателями.
- **Как проверяли:** обязательные HTTP-тесты I1–I4 на отдельной PostgreSQL; дополнительные проверки адресатов, ошибок, пустых массивов, разделения портов и отсутствия имён в логах. Тестовые фикстуры независимы от seed; отдельный тест сверяет seed с общим контрактом. Общий `go test ./...` с обязательной БД и `go vet ./...` прошли.
