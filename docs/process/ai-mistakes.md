# Ошибки ИИ и как мы их исправили

Материал для критерия К2 («работа с ошибками ИИ»). Формат: что произошло, как заметили, как исправили, какое правило вынесли.

## M1. Правка «прошла», но файл не изменился

- **Дата и этап:** 2026-11-08, этап 2
- **Инструмент:** Claude Code
- **Что произошло:** агент обновлял `docs/progress.md` Python-скриптом через `python`. На Windows `python` оказался заглушкой Microsoft Store: команда ничего не сделала и не вернула ошибку, а агент уже закоммитил изменения.
- **Как заметили:** после коммита агент сам проверил результат (`grep` по ожидаемой строке) и получил 0 совпадений.
- **Как исправили:** правки внесены точечным редактированием файла, коммит дополнен.
- **Правило:** после любой автоматической правки проверять результат, а не код возврата. Войдёт в `AGENTS.md` как «проверяй, что изменение действительно применилось».

## M2. Неверный юридический термин в каталоге услуг

- **Дата и этап:** 2026-11-08, этап 3 (ошибка) → этап 4 (исправление)
- **Инструмент:** Claude Code
- **Что произошло:** при составлении каталога ИИ назвал мгновенную справку для действующего студента «справкой об обучении» и включил в каталог «академическую справку».
- **Как заметили:** на этапе 4 команда попросила проверить соответствие законам. ИИ стал искать ст. 60 273-ФЗ и нашёл, что «справка об обучении / о периоде обучения» выдаётся отчисленным и не прошедшим итоговую аттестацию, а академические справки не выдаются с 2013 года.
- **Как исправили:** услугу переименовали в «справку с места учёбы (подтверждение статуса обучающегося)», академическую справку заменили выпиской оценок (D30).
- **Правило:** юридические и официальные термины сверяем с первоисточником до того, как они попадут в интерфейс.

## M3. Контракты не прошли линтер OpenAPI

- **Дата и этап:** 2026-11-08, этап 5
- **Инструмент:** Claude Code (написал контракты) + Redocly CLI (проверка)
- **Что произошло:** ИИ написал 7 OpenAPI-файлов. Своим скриптом он проверил только ссылки `$ref`, потому что скачивать линтер в его сессии было запрещено. Капитан запустил линтер вручную: **13 ошибок**. Восемь из них — поля вида `allOf: [$ref] + nullable` без явного `type` (в OpenAPI 3.0 это недопустимо и могло сломать генерацию кода). Ещё пять — у внутренних API не указано, что аутентификации нет.
- **Как исправили:** ИИ добавил `type` скриптом и проверил результат подсчётом (8 из 8). У внутренних API явно указал `security: []` с пояснением (защита — изоляция сети, D31). Добавил описания тегов и `redocly.yaml` с объяснением отключённых правил. Повторный запуск — 0 ошибок, 0 предупреждений.
- **Правило:** самодельная проверка не заменяет настоящий валидатор. Линтер контрактов — обязательный шаг в CI и в задаче каркаса.

## M4. Две недоработки в контракте `auth`, которые нашлись только при реализации

- **Дата и этап:** 2026-11-08, реализация T02
- **Инструмент:** Claude Code (писал контракт на этапе 5 и сам же реализовывал сервис)
- **Что произошло:**
  1. у ответа `POST /logout` (204) в контракте не был описан заголовок `Set-Cookie` — сгенерированный код не позволял очистить cookie сессии;
  2. заголовок `X-Faculty-Id` (есть только у сотрудника) генератор сделал обязательным — студенту ушёл бы «нулевой» UUID факультета.
- **Как заметили:** при реализации по сгенерированным интерфейсам; линтер OpenAPI такие смысловые ошибки не ловит.
- **Как исправили:** в контракт добавлен `Set-Cookie` у logout; для проверки сессии написан свой тип ответа, который ставит `X-Faculty-Id` только сотруднику, с комментарием почему; тест «у студента нет X-Faculty-Id».
- **Правило:** контракт считается готовым, только когда по нему сгенерирован и скомпилирован код и написан хотя бы один хендлер.

- **Дата и этап:** 2026-11-08, реализация T08
- **Инструмент:** Claude Code (основная сессия + субагент T08)

## M6. Пароли тестовых аккаунтов попали в вывод команды

- **Дата и этап:** 2026-11-08, проверка оценки ответа деканата на стенде
- **Инструмент:** Claude Code (основная сессия)
- **Что произошло:** чтобы узнать логины, агент вывел строки таблицы из `.secrets/demo-accounts.md` и отрезал колонку пароля через `cut`. Но `cut` убрал только последнюю колонку («роль»), и локальные пароли тестовых аккаунтов оказались в выводе команды, то есть в журнале сессии. В репозиторий они не попали: `.secrets/` в `.gitignore`.
- **Как заметили:** агент сам увидел пароли в выводе и сообщил капитану.
- **Последствия:** это пароли локального стенда. Финальные пароли для жюри генерируются заново при деплое (T23), поэтому утёкшие нигде, кроме ноутбука капитана, не действуют.
- **Правило:** файл секретов не выводить даже частично. Нужен пароль — читать его в переменную оболочки (через `awk`, без вывода на экран) и передавать в запрос через временный файл, который сразу удаляется. Так сделана проверка на стенде в этом же PR.

## M10. Неуточнённое имя id в UPDATE с подзапросом

- **Дата и этап:** 2026-11-09, T04 PR2, генерация SQL-обёрток.
- **Инструмент:** Codex.
- **Что произошло:** в запросе обновления занятия агент написал `WHERE id = ...`, добавив рядом подзапрос к группам для проверки факультета. Генератор sqlc сообщил `column reference "id" is ambiguous`.

- **Правило:** в SQL с несколькими источниками явно указывать таблицу для идентификаторов, в том числе в UPDATE с EXISTS.

## T04. Отмена перенесённого занятия использовала исходную дату

- **Дата / инструмент:** 2026-11-09, Codex, дополнительное ревью по запросу участника.
- **Ошибка:** `prev_*` хранит слот до первого изменения для отображения расписания. Формирователь события использовал его и при отмене: занятие, перенесённое с 17-го на 19-е, порождало уведомление об отмене 17-го.
- **Исправление:** для отмены `previous` и `current` события равны фактическому отменённому слоту. Исходный слот ответа API сохраняется. Общая функция исправляет и live-публикацию, и replay.
- **Проверка:** воспроизводивший ошибку тест функции; интеграционный сценарий PostgreSQL + NATS: перенос → смена аудитории → отмена → live-событие и replay. Проверяются дата, время и новая аудитория, а также сохранение исходной даты в API.
- **Правило:** различать исторический слот интерфейса и фактический слот отменяемого занятия; проверять последовательности изменений, а не только каждую операцию отдельно.

## T04. Частичное исправление было выдано без сверки с полным ревью

- **Дата / инструмент:** 2026-11-09, Codex.
- **Ошибка:** агент исправил отмену после переноса, но не прочитал уже опубликованные замечания капитана. При следующем переносе и смене аудитории событие всё ещё брало первый слот; остальные восемь пунктов полного ревью оставались открытыми. Участник указал на неполноту отчёта.
- **Исправление:** live-событие берёт `previous` из заблокированной строки до UPDATE при любом типе изменения. API по-прежнему хранит первый слот. Группы расписания, ICS и seed-replay загружаются пакетно. Добавлены лимиты корпуса/аудитории по 100 символов, текст ошибки публикации в лог, даты seed от `now()`, пустой ICS при обратном периоде; удалена ссылка на удалённый снимок. Годы поступления — 2025/2024 по ревью PR #19 и уточнению D53 капитана.
- **Проверка:** цепочка перенос 17→19→20 → аудитория → отмена проверяет фактический предыдущий слот каждого live-события. Pgx-трассировщик проверяет ровно один запрос групп для студента, сотрудника, ICS и replay. Усилены полные ожидания A8/A17; проверены границы 100/101 символов, свежесть seed, годы поступления и обратный период календаря. Все Go-тесты с обязательной БД и `go vet ./...` проходят.
- **Правило:** полный список ревью должен иметь проверяемый статус каждого пункта. Проверка собственных находок не заменяет замечания ревьюера.
