# Материалы Всеволода Омельченко для T24

Обновлено 10 ноября 2026 года. Это описание моей части проекта для общего документа команды. Код T04, T09, T14, T15 и T16 уже объединён с main; итоговый PDF собирает капитан.

## 1. Какую проблему решаем

Студенту приходится искать расписание, оценки и сведения об обращениях в разных местах. В моей части кабинета эти данные собраны на четырёх экранах: «Сегодня», «Расписание», «Успеваемость» и «Профиль». На главной видна ближайшая пара, в расписании — переносы и отмены, в успеваемости — набранные баллы и результаты сессий. Сотрудник деканата может изменить занятие, а получатель справки — проверить её по коду без входа.

Разделы выбрали по конкурсному заданию и плану команды. Чтобы узнать, насколько они нужны студентам, 9 ноября опубликовали [анонимный опрос](https://forms.yandex.ru/u/6af1aef56d2d730da9e02707/). На последней проверке 9 ноября ответов ещё не было. План — собрать не менее 15 ответов до 13 ноября и подготовить выводы до 14 ноября. После сбора результатов команда сможет сопоставить ответы с решениями в интерфейсе.

[Вопросы анкеты и план анализа](https://github.com/4RH1T3CT0R7/mgimo-digital-dean/blob/227b8dcf5cf676a564bd100ea5b6c383f23c2989/docs/process/survey.md).

## 3. Как работали с ИИ

Перед реализацией Codex читал правила проекта, задачу и контракты API. Сначала выполнялись обязательные сценарии из ТЗ, затем — исправления по ревью. Каждая задача шла отдельным PR; капитан проверял изменения и объединял их с main.

| Запрос или решение | Результат |
|---|---|
| «Начинай работу» | Реализация academic: сначала схема БД и внутренний API, затем расписание, оценки и события. |
| «Если можешь исправить на данном этапе, то исправляй» | Проверка найденных ошибок и замечаний капитана. После неполного исправления пришлось заново сверить весь список ревью. |
| «Да, сохранить формат A–Z и 2–7» | В T15 оставили формат кода из контракта. Положительный пример с недопустимой цифрой 9 заменили на K7M2QX4P7A. |
| «Нет, только мою часть» | T06 осталась за Владиславом; работа ограничена моими задачами. |
| «Проверь все пункты, кроме календаря на естественность» | Вычитка интерфейса и материалов после слияния с main: более простые подписи, исправление грамматики и устаревших статусов. |

[Журнал запросов](prompts.md) содержит подробности по этапам. Автоматические тесты дополнялись ручной проверкой: зелёный тест сам по себе не показывает, удобно ли читать экран и работает ли установка в браузере.

## 5. Какие ошибки пришлось исправить

| Ошибка | Что изменили |
|---|---|
| Codex закрыл только часть замечаний ревью, но сообщил об исправлениях слишком обобщённо | Сверили каждый пункт с кодом и проверками: [T04](review-t04.md), [T14](review-t14.md), [T16](review-t16.md). |
| При повторном переносе в событие попадал первоначальный слот вместо состояния перед последним изменением | Разделили данные для истории расписания и события. Добавили проверки цепочки «перенос → перенос → аудитория → отмена». |
| При выходе вместе с личными данными сбрасывалась тема | Сохранили настройку темы, оставив очистку данных и кэша. Проверили выход и ошибки хранилища. |
| Заголовок и вариант ответа в Яндекс Формах не сохранились | Восстановили поля и проверили их после перезагрузки редактора и в опубликованной форме. |
| Локальный стенд выключился во время сбора снимков PWA | Увеличили время работы стенда с 30 до 120 минут, повторно проверили вход и загрузку профиля. |

Подробности и выводы записаны в [журнале ошибок ИИ](ai-mistakes.md). В протоколах сохранены неудачные шаги, для которых есть снимки: например, [перенос с незаполненной датой](screenshots/runtime-api/transfer-date-empty-tool-360-dark.jpg) и [предупреждения Manifest](screenshots/t16/manifest-before-warnings.png).

## 6. Как защищены данные

После входа сервис auth проверяет сессию, а шлюз передаёт academic сведения о пользователе. Студент получает расписание и оценки только для своей учётной записи. Сотрудник работает с группами своего факультета. При попытке открыть чужой объект API отвечает «не найдено»; эти ограничения проверяются тестами с отдельными БД.

Academic хранит учебные сведения в собственной БД. С другими сервисами он обменивается данными через внутренний API и события. Все студенты и их учебные данные в прототипе вымышленные.

Сессия хранится в защищённой cookie, доступ к которой закрыт для JavaScript. После выхода из интерфейса удаляются загруженные личные данные и Cache Storage; выбранная тема сохраняется. PWA кэширует файлы приложения, но не ответы API. Пустой Cache Storage после выхода подтверждён снимком.

Размещение сервера в России, домен и настройку опубликованного стенда капитан описывает в T23 после развёртывания.
