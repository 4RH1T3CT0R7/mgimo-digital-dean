# Как работать с задачами (плейбук для Codex и Claude Code)

Этот файл читают **участники и их агенты** перед каждой задачей. Он нужен, чтобы агент не «косячил»: работал по шагам, проверял себя и останавливался там, где нужно решение человека.

## 1. Перед началом
1. `git checkout main && git pull`
2. `git checkout -b tNN-кратко` (например, `t04-academic-pr1`)
3. Открой файл своей задачи в `docs/tasks/` и прочитай его сам: ты отвечаешь за результат, агент — только инструмент.

## 2. Промпт для агента (вставлять целиком)

```text
Ты работаешь в репозитории mgimo-digital-dean (личный кабинет студента, конкурсный прототип).
1. Прочитай AGENTS.md и docs/tasks/README.md.
2. Выполни задачу из docs/tasks/<ФАЙЛ>.md<, только часть PR1 — если задача разбита на PR>.
3. Работай строго по шагам из раздела «Что сделать». После каждого шага запускай проверки
   из раздела «Критерии готовности», которые уже можно запустить, и исправляй ошибки.
4. Тест-кейсы из ТЗ реализуй ровно с теми входами и ожидаемыми значениями, что в таблицах.
   Тест не проходит — исправляй код, а не тест. Тесты не пропускай и не отключай.
5. Не меняй файлы вне своих каталогов (таблица владения в AGENTS.md), контракты docs/contracts/*
   и сгенерированный код. Если контракт кажется неверным или неполным — ОСТАНОВИСЬ
   и опиши проблему в отчёте; не обходи её.
6. Не добавляй зависимостей, которых нет в ТЗ или docs/architecture.md §7.
7. В конце выведи отчёт:
   а) что сделано по пунктам «Что сделать»;
   б) какие проверки запускались — с последними строками вывода команд;
   в) что не сделано или вызывает сомнения;
   г) отметки по каждому пункту «Критериев готовности».
```

Если агент остановился с вопросом — не придумывай за него ответ, напиши капитану.

## 3. Проверка результата человеком
Агент может отчитаться «всё готово», а на деле нет. Проверь сам:

| Что проверить | Как |
|---|---|
| Тесты действительно запускались и прошли | Сам запусти команды из «Критериев готовности», посмотри на вывод |
| Тесты не подогнаны | `git diff` по файлам `*_test.go` / `*.test.ts`: нет `t.Skip`, закомментированных проверок, изменённых ожидаемых значений из таблиц ТЗ |
| Не тронуты чужие файлы | `git status` / `git diff --stat main`: изменения только в твоих каталогах |
| Сгенерированный код не правился руками | `make gen` (или `npm run gen`) не даёт изменений |
| Интерфейс работает на телефоне | Открой экран, в DevTools включи ширину **360 px**: нет горизонтальной прокрутки, всё нажимается |
| Есть состояния загрузки, пустоты и ошибки | В режиме моков переключи сценарий (см. T08) или отключи сеть в DevTools |

## 4. Типичные ошибки агентов и как их поймать

| Ошибка | Как заметить |
|---|---|
| Пишет типы запросов/ответов руками вместо сгенерированных | Поиск по коду: структуры с теми же полями, что в `internal/api` или `src/api` |
| Правит сгенерированный код или контракт, чтобы «всё сошлось» | `git diff` по `internal/api`, `src/api`, `docs/contracts` — должно быть пусто |
| Забывает фильтр по владельцу в SQL | В каждом запросе для `/me/*` есть `student_id = $…`; тест «чужое → 404» из ТЗ проходит |
| Подгоняет тест под код | Ожидаемые значения в тестах совпадают с таблицами ТЗ |
| Захардкодил данные на экране вместо запроса к API | В компоненте нет массивов с «живыми» данными; данные приходят из хуков TanStack Query |
| Нет состояний загрузки, пустоты, ошибки | Отключить сеть / пустой ответ мока → экран не пустой и не «белый» |
| Английский текст в интерфейсе | Пройтись по экрану глазами |
| Тянет лишнюю библиотеку | `git diff go.mod frontend/package.json` |
| Делает больше, чем просили | Сравнить с разделом «Что не входит» |

## 5. Pull request
- Заголовок: `TNN: <название задачи>` (для частей: `T04 PR1: …`).
- Описание: что сделано; отчёт агента (раздел «г» — отметки по критериям); для интерфейса — **скриншоты 360 px и 1280 px**.
- Дождись **зелёного CI**. Красный CI — дай агенту лог ошибки и попроси исправить.
- Ревьюер — капитан. Замечания ревью отдавай агенту как есть, с номером строки.

## 6. Запиши для жюри (обязательно)
Критерий К2 оценивает, **как** мы работали с ИИ. После каждой задачи допиши в конец файлов:
- `docs/process/prompts.md` — ключевой промпт и что получилось (формат — как в существующих записях);
- `docs/process/ai-mistakes.md` — если агент ошибся: что сделал, как заметили, как исправили;
- скриншоты удачных и неудачных вариантов — в `docs/process/screenshots/` с понятными именами (`T09-schedule-360-v1.png`).

## 7. Тесты с базой данных (для T04, T06)
- Тесты, которым нужна PostgreSQL, используют `pkg/platform/platformtest` (делает капитан в T02): он создаёт отдельную базу на тест и применяет миграции.
- **Локально** такие тесты запускаются, если задан `TEST_DATABASE_URL`. Поднять базу можно командой `make up` или `docker compose -f deploy/docker-compose.yml up -d postgres`. Без переменной тесты помечаются как пропущенные.
- **В CI** они выполняются обязательно: там задано `REQUIRE_DB_TESTS=1`, и пропуск превращается в падение. Если у тебя Codex в облаке без Docker, проверка этих тестов — зелёный CI в PR.
