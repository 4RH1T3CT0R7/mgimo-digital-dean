## 1. Функциональные требования (обязательное ядро)

| ID | Раздел | Что сказано в задании | → Что из этого следует |
|----|--------|-----------------------|------------------------|
| F1 | Вход и профиль | Вход по логину и паролю (или другим способом). Профиль: ФИО, факультет, направление, курс, группа | Регистрация не нужна, аккаунты заводим заранее (seed) |
| F2 | Расписание | Занятия на сегодня и на неделю, аудитория и преподаватель, **заметные** изменения и переносы | У занятия нужен признак «изменено/перенесено» с явной подсветкой |
| F3 | Успеваемость | Оценки и зачёты по дисциплинам, сессия, понятная картина «как у меня дела с учёбой» | Нужна сводка (средний балл, долги, прогресс), одной таблицы мало |
| F4 | Заявки и справки | Заказ справки или подача заявления онлайн, статус заявки | Форма, список заявок, статусы. Кто меняет статус — см. Н2 |
| F5 | Уведомления | Новости и объявления деканата, напоминания о дедлайнах и изменениях | Лента связана с F2 (переносы) и F4 (смена статуса), плюс дедлайны |

Сквозные свойства: всё в одном месте (учёба, документы, связь с деканатом); нужное находится за пару касаний без инструкций; красиво; работает с телефона; безопасно.

Опционально: свои идеи и дизайнерские решения («позволят выделиться»); кабинет сотрудника (упоминается только в пункте про тестовые аккаунты: «если есть»).
Ключевая фраза задания: «главное — не количество разделов, а то, насколько продуманно и удобно они работают вместе».

## 2. Нефункциональные требования

| Группа | Требование |
|--------|------------|
| Прототип | Рабочий, открывается по ссылке. Сквозной сценарий: войти → расписание → оценки → подать заявку → увидеть статус. Figma и картинки не считаются |
| Стек | Любой, но «адекватный задаче и гибкий с точки зрения масштабирования под различное количество пользователей» |
| Разработка | Код пишут ИИ-ассистенты. Обязательно уметь ставить задачу ИИ и проверять результат |
| Мобильность | Все основные сценарии работают на ширине от 360 px |
| Данные | Только вымышленные. Не подключаться к системам вуза, не использовать настоящие логины. Парсинг открытых данных (например, расписания) разрешён |
| Бренд | На сайте должно быть понятно, что это концепт для конкурса, а не официальный сервис. Официальный логотип нельзя, свой «по мотивам» можно |
| Лицензии | Библиотеки, шрифты, иконки и картинки только с разрешающей лицензией |
| Безопасность | (1) чужой профиль или заявку не открыть даже подменой адреса (защита от IDOR); (2) пароли не хранятся в открытом виде; (3) ключи сервисов, в т.ч. ИИ, не лежат в коде и в браузере |
| Доступность | Открывается из России без VPN и работает до 28 ноября (объявление итогов). Хостинг любой |
| Тест-аккаунты | Минимум 2 студента с разными данными. Если есть кабинет сотрудника, то и его аккаунт |

### Что сдать

Отправляет капитан; приём с 08.11 19:00 МСК; принимается последняя версия.

1. Ссылка на прототип и логины/пароли тест-аккаунтов в комментарии.
2. Исходный код: репозиторий (GitHub/GitVerse) с доступом для жюри или архив.
3. Описание процесса (PDF или документ по ссылке) со скриншотами:
   - какую проблему решаем, почему именно эти разделы, опрос однокурсников (если был);
   - полный перечень ИИ-инструментов, IDE и сервисов с назначением каждого;
   - ключевые промпты и диалоги с привязкой к этапам и функциям;
   - скриншоты от первой идеи до готового кабинета, включая неудачные варианты;
   - как устроены вход, хранение данных и защита, простыми словами;
   - что сделано вручную.
4. Видео до 5 минут, в том числе с телефона. Необязательно, но приветствуется.

## 3. Критерии оценки — чек-лист

Четыре критерия по 10 баллов, итог — среднее по экспертам. Веса подпунктов в задании не заданы: ниже наша разбивка формулировок на проверяемые пункты.

### К1. Проработанность идеи (10)
- [ ] Проблема студентов сформулирована (и, желательно, подтверждена опросом однокурсников)
- [ ] Сценарии построены вокруг реальных задач, а не вокруг разделов
- [ ] Обязательное ядро F1–F5 реализовано полностью
- [ ] Есть сильные и смелые идеи, которые меняют опыт общения с деканатом (повышают оценку)

### К2. Масштаб использования нейротехнологий (10)
Оценивается ИИ **в процессе разработки**, а не внутри продукта.
- [ ] Продуманный процесс работы с ИИ
- [ ] Качество промптов и постановки задач ассистентам и **субагентам**
- [ ] Структура документов и файлов для ИИ-агентов (CLAUDE.md, AGENTS.md, docs/, ТЗ)
- [ ] Работа с ошибками ИИ: что сломалось и как исправили
- [ ] ИИ-инструменты для дизайна и контента, не только для кода
- [ ] Полное и наглядное описание процесса

### К3. Имплементация (10)
- [ ] Прототип открывается, основные сценарии проходят без ошибок
- [ ] Данные сохраняются: заявка переживает перезагрузку и повторный вход. Нужна настоящая БД
- [ ] Полноценная работа на телефоне
- [ ] Безопасность: только свои данные, хеши паролей, секреты вне кода и браузера
- [ ] Только вымышленные данные
- [ ] Тест-аккаунты работают
- [ ] Соблюдены прочие требования: дисклеймер, свой логотип, лицензии, доступ из РФ

### К4. Качество (10)
- [ ] Современный и цельный визуальный стиль
- [ ] Понятная навигация, нужное находится быстро
- [ ] Продуманы пустые состояния, ошибки и загрузка (на каждом экране)
- [ ] Интерфейс быстрый и доступный (a11y)
- [ ] «Хочется пользоваться каждый день»

### Выводы, которые влияют на план
- К2 начисляется за артефакты процесса: журнал промптов, ошибки ИИ, скриншоты промежуточных версий. Собирать их задним числом тяжело, поэтому ведём с первого дня (`docs/process/`).
- ИИ-функция внутри кабинета не требуется. Она может добавить баллов в К1 как «смелая идея», но тогда нужен серверный ключ и решение проблемы доступа к LLM-API из РФ.
- Из К3 и К4 следует, что нужны реальный бэкенд с БД и три состояния (пусто, ошибка, загрузка) на каждом экране.
- Требование масштабируемости сформулировано как «адекватный и гибкий стек». Микросервисы в задании не требуются. Сравнение вариантов — на этапе 4 (`architecture.md`).
