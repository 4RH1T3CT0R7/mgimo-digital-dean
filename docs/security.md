# Безопасность и соответствие законодательству

Статус: этап 4, 2026-11-08. Решение D29.

> **Важно.** В прототипе только вымышленные данные (требование задания). Формально они не являются персональными данными по 152-ФЗ: за ними нет реальных людей. Но систему мы строим так, **как если бы данные были реальными**, чтобы её можно было внедрить в вуз без перепроектирования.
>
> Ссылки на нормы ниже — результат нашего анализа, а не юридическое заключение. Пункты с пометкой «предварительно» нужно сверить с актуальной редакцией на pravo.gov.ru или consultant.ru.

## 1. Какие нормы нас касаются

| Норма | О чём | Что это значит для нас |
|---|---|---|
| **152-ФЗ «О персональных данных»**, ст. 5 | Обработка ограничена целью; избыточные данные не собираются | Минимизация: не храним гражданство, пол, паспорт, медицинские данные (D18). У каждого поля профиля есть причина |
| 152-ФЗ, ст. 18.1 ч. 2 | Оператор публикует документ о политике обработки ПДн | Страница «Политика обработки персональных данных» в кабинете (демонстрационная, от имени команды-концепта) |
| 152-ФЗ, ст. 18 ч. 5 (локализация, введена 242-ФЗ) | Базы с ПДн граждан РФ находятся в России | VPS в РФ (D6). Из браузера никаких запросов к зарубежным сервисам: шрифты и иконки размещаем у себя |
| 152-ФЗ, ст. 19 | Правовые, организационные и технические меры защиты, определение угроз | Модель угроз (§3) и технические меры (§4) |
| **ПП РФ № 1119** | Уровни защищённости ИСПДн (УЗ-1 — строжайший, УЗ-4 — базовый) | Для реального внедрения, *предварительно*: «иные» категории ПДн, угрозы 3-го типа, до 100 000 субъектов → **УЗ-4**. Сверить с текстом постановления |
| **Приказ ФСТЭК № 21** | Состав мер защиты для каждого уровня | Технические меры в §4 сгруппированы по его группам (ИАФ, УПД, РСБ, ЗИС, ОЦЛ, АНЗ). Сертифицированные средства защиты и аттестация — задача реального внедрения, не прототипа |
| **149-ФЗ «Об информации…»**, ст. 10 ч. 2 | Распространяемая информация должна содержать сведения об обладателе | В подвале каждой страницы: кто сделал прототип, что это концепт для конкурса, а не официальный сервис МГИМО (заодно требование задания) |
| 149-ФЗ, ст. 16 | Обладатель информации обязан её защищать | Весь раздел §4 |
| **273-ФЗ «Об образовании»**, ст. 60 ч. 12 | «Справка об обучении / о периоде обучения» — документ для отчисленных или не прошедших итоговую аттестацию | Термин для действующего студента не используем. Наша мгновенная справка — «справка с места учёбы», то есть подтверждение статуса обучающегося (D30) |
| **63-ФЗ «Об электронной подписи»** | Юридическая значимость электронного документа | PDF-справка в прототипе без электронной подписи, с водяным знаком «концепт, не документ» и кодом проверки. При реальном внедрении — подпись вуза |
| ГОСТ Р 52872-2019 (доступность интернет-ресурсов) | Доступность для людей с нарушениями зрения | Ориентир — WCAG 2.1 AA: контраст, подписи полей, работа с клавиатуры (заодно критерий «Качество») |

Обязательных для нас законов об ИИ сейчас нет. Для помощника (I5) применяем 152-ФЗ: персональные данные в LLM не отправляем (§4). Ответы помечаем как ответы ИИ, который может ошибаться.

## 2. Что мы храним и зачем (минимизация)

| Данные | Зачем | Кто видит |
|---|---|---|
| ФИО, факультет, направление, курс, академическая и языковая группа | Требование F1; расписание; разграничение доступа | Сам студент; сотрудник своего факультета в заявках |
| Номер студенческого билета, форма и основа обучения | Профиль, справка с места учёбы | Сам студент; сотрудник своего факультета |
| Логин, хеш пароля (bcrypt) | Вход | Никто: пароль не восстанавливается из хеша |
| Оценки, расписание | F2, F3 | Сам студент |
| Заявки, переписка, вложения | F4, I3 | Студент-автор; сотрудник своего факультета; администратор |

**Не храним:** гражданство, пол, паспортные данные, адрес, медицинские сведения, фото.

## 3. Модель угроз (кратко)

| Угроза | Как защищаемся |
|---|---|
| Студент открывает чужую заявку, подставив другой ID в адрес (IDOR) | Эндпоинты `/me/...`, ID владельца берётся только из сессии, фильтр в SQL, ответ 404. **Автотест** |
| Подделка заголовков `X-User-*` | Caddy удаляет их из входящих запросов; сервисы недоступны снаружи |
| Подбор пароля | Ограничение неудачных попыток на логин и на IP, задержка; одинаковое сообщение «неверный логин или пароль» (не раскрываем, существует ли логин) |
| Кража сессии | Cookie `HttpOnly; Secure; SameSite=Lax`; новый токен при входе; срок жизни; выход удаляет сессию в БД |
| CSRF | `SameSite=Lax` + запросы, меняющие данные, принимают только `application/json` |
| XSS | React экранирует вывод; `dangerouslySetInnerHTML` запрещён; строгая CSP (`default-src 'self'`) |
| SQL-инъекция | Только параметризованные запросы, сгенерированные sqlc |
| Вредоносный файл во вложении | Лимит размера, белый список типов, хранение вне веб-корня, отдача только через проверку прав, `Content-Disposition: attachment` |
| Утечка ключей | Секреты только в переменных окружения на сервере; `.env` в `.gitignore`; в репозитории только `.env.example`; ключ LLM только у `assistant` |
| Уязвимые зависимости | `govulncheck` и `npm audit` в CI |
| Утечка ПДн через логи | В логах только ID и типы событий |
| Потеря данных до 28.11 | Ежедневный `pg_dump`, том PostgreSQL вне контейнера |
| Передача ПДн третьим лицам через ИИ (I5) | В запрос к LLM уходит только текст вопроса, без профиля; предупреждение «не вводите персональные данные» |
| Перехват трафика | Только HTTPS (Caddy), HSTS |

## 4. Технические меры (по группам Приказа ФСТЭК № 21)

| Группа | Меры в прототипе |
|---|---|
| **ИАФ** — идентификация и аутентификация | Логин и пароль; bcrypt; защита от перебора; срок жизни сессии; новый токен при входе |
| **УПД** — управление доступом | Роли студент / сотрудник / администратор; фильтр по владельцу и факультету в каждом запросе; 404 на чужое; минимальные права пользователей БД (своя БД у каждого сервиса) |
| **РСБ** — регистрация событий безопасности | Журнал в stdout (JSON): входы, неудачные попытки, отказы в доступе, смена статусов заявок — с ID пользователя, без ПДн |
| **ЗИС** — защита информационной системы и каналов | HTTPS + HSTS; изолированная внутренняя сеть Docker; заголовки CSP, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'` |
| **ОЦЛ** — целостность | Валидация входных данных по контракту (OpenAPI); резервные копии БД |
| **АНЗ** — анализ защищённости | Проверка зависимостей в CI; автотесты на права доступа |

## 5. Что показываем пользователю

- Подвал на каждой странице: «Концепт для конкурса „Цифровой деканат будущего“. Не является официальным сервисом МГИМО. Все данные вымышлены» + сведения о команде (149-ФЗ ст. 10, требование задания).
- Страница «Политика обработки персональных данных» (152-ФЗ ст. 18.1): какие данные, зачем, как защищены, сроки хранения.
- Cookie используется только одна — сессионная, строго необходимая. Аналитику и сторонние счётчики не подключаем, поэтому баннер о cookie не нужен.
- Раздел «Как мы защищаем ваши данные» простыми словами. Он же пойдёт в описание процесса для жюри.

## 6. Чек-лист перед сдачей (входит в план)

- [ ] Автотест IDOR (чужая заявка → 404) проходит через шлюз
- [ ] Заголовки `X-User-*` снаружи игнорируются (проверено запросом)
- [ ] В репозитории нет секретов (`git log -p` + сканер секретов)
- [ ] Пароли в БД — только bcrypt-хеши
- [ ] Из браузера нет запросов к сторонним доменам (вкладка Network)
- [ ] Подвал и политика обработки ПДн на месте
- [ ] HTTPS, HSTS, CSP включены
- [ ] Резервная копия БД снимается и восстанавливается
